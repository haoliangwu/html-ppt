举手示意一下 —— 有多少人在日常使用技能？有多少人自己写过？

好。我观察到的是大多数人用技能，但很少人写技能。为什么？我认为有四个痛点。

第一，技能太多了。打开一个技能仓库，几百个。每个都有长长的文档。人都懒 —— 我们不会去读完。

第二，就算找到，也可能不 work。试一下，不适合你的场景，花更多时间去调整。

第三，也是我觉得最关键的一点 —— 人们把技能神秘化了。觉得写技能需要什么特殊的专业知识。但技能就是一个有格式的 prompt。如果你能写 prompt，你就能写技能。

第四，试错成本很高。一个设计不好的技能可能包含几百行。每次使用，AI 都要全部读完。如果质量低，你就要反复重做 —— 每次重做又是一轮 token 消耗。所以技能质量直接关联 token 效率。

今天我给出的答案聚焦在痛点三和四 —— 如何设计出纯粹、高效、组合后威力倍增的技能。答案就是函数式思维。

在深入函数式思维之前，我需要做一件事 —— 把技能解构掉。

一个技能文件里有什么？一段 system prompt，一些触发条件，也许还有一些约束规则。本质上，和你每天在 Cursor 里写的 system prompt 没有区别。唯一的区别：技能有格式规范 —— 放在哪、有什么元数据、如何触发。

这个"结构"给了你什么？三样东西。

第一，消除了重复的 prompt engineering。你知道那种感觉 —— 每个新项目、每次新对话，都要复制粘贴一大段 system prompt。技能解决了这个问题。加载一次，集中维护，到处更新。

第二，共享和复用。你写了一个处理 Bitbucket PR 的技能 —— 你的同事也需要同样的能力。直接加载就行，不需要从零写。这对团队效率提升巨大，因为 prompt engineering 非常个人化 —— 每个人的输出质量差异很大。

第三，也是最重要的 —— 从最简单的开始。很多人觉得技能得覆盖完整的工作流才有价值。错了。一个只做好一件事的技能 —— 比如"从 CLI 获取 git diff" —— 用对了就已经很强大。别让神秘的印象吓到你。

好，解构完成。现在进入核心：函数式思维如何应用到技能设计。

// 第二幕 · 函数式思维

函数式思维
→ 技能设计

🧩 单一职责

一个函数只做一件事，并把它做好。

→ 一个技能覆盖一个领域，并把它做好。

"无所不能"的技能 = 难以维护、复用、组合

🔗 组合

复杂行为从简单函数的组合中涌现。

→ 两个简单技能组合 = 一个更强大的技能

AI 自动推断给定任务该加载哪些技能

"像写纯函数一样写你的技能
   — 单一职责、可组合、无副作用"

函数式编程的两个核心原则 —— 相信大家都很熟悉。让我意外的是，很少有人把它们应用到技能设计上。

第一：单一职责。一个函数只做一件事，并把它做好。在技能世界里，就是一个技能覆盖一个业务领域。我见过太多"巨无霸技能" —— 比如一个叫"全栈开发助手"的，把前端、后端、数据库、部署、测试……全塞进一个文件。结果呢？AI 每次都要读几千行，而且那些指令甚至可能互相冲突。维护简直是灾难。

第二：组合。在函数式世界里，复杂行为不是写复杂函数来的 —— 是组合简单函数来的。在技能世界里，两个足够简单纯粹的技能组合在一起，威力远不止相加。而且今天可能最重要的一个洞察 —— AI 会自动推断加载哪些技能。

它看到你的任务描述里有"review 这个 PR"，就加载代码审查技能。看到"从 Bitbucket 获取"，就加载 Bitbucket CLI 技能。这种推断能力，正是你函数式设计的结果 —— 因为每个技能的责任边界足够清晰，AI 能准确判断"哪个技能适用于此"。

用一个真实案例来演示。

// 第二幕 · 案例研究

代码审查案例：
两种设计

❌ 非函数式

一个 "巨无霸" 代码审查技能：

  • 从 Bitbucket 拉取 PR diff
  • 解析 diff 文件
  • 对照本地代码库分析
  • 生成审查意见
  • ...全在一个文件里

换到 GitHub？重写。换审查策略？重写。

✅ 函数式

拆成 三个 独立技能：

  • using-bitbucket-cli — 获取 PR 数据
  • java-best-practices — 审查策略（代码规范、技术栈、性能、安全）
  • requesting-code-review — 描述审查流程（抽象掉"数据从哪来、如何审查"）

换到 GitHub？把 Bitbucket CLI 换成 GitHub CLI。换 Python？换审查策略技能。其他技能：零修改。

💡 AI 推断是关键 — 它看到"审查这个 Java PR"然后自动加载 using-bitbucket-cli + java-best-practices + requesting-code-review

好，用我实际使用的一个真实案例来验证刚才说的一切。这是一个代码审查场景。

左边 —— 非函数式设计 —— 那是我最初的做法。我写了一个巨大的技能，把"如何从 Bitbucket 拉 PR"、"如何解析 diff"、"如何生成审查意见"全塞进一个文件。然后发生了什么？

一个月后我要审查一个 GitHub 仓库。技能完全废了 —— "拉取 PR"那部分硬编码了 Bitbucket 的 API。我要么重写整个技能，要么新建一个 GitHub 版本。两种都意味着大量的重复劳动。

右边是重构后的版本。我把它拆成 三个技能：一个处理"获取外部数据"（Bitbucket CLI），一个处理"审查策略"（java-best-practices），第三个处理"审查流程"（requesting-code-review）。

为什么要有第三个？因为审查代码不只是检查语法 —— 你需要一个策略。对 Java 来说，可能意味着检查代码规范、技术栈约束、性能模式、安全问题。审查流程技能是通用的 —— 它描述如何审查。但 java-best-practices 描述审查什么。两个不同的职责。

AI 怎么知道加载全部三个？通过推断。AI 看到你的任务描述提到 Java 审查和 PR，就自动加载 using-bitbucket-cli 获取数据，java-best-practices 获取审查策略，requesting-code-review 获取流程。

结果呢？灵活性。当项目迁移到 GitHub 时，我只需把 using-bitbucket-cli 换成 using-gh-cli。审查 Python 项目时，把 java-best-practices 换成 Python 审查策略技能。核心的审查流程技能从不需要改动。这种灵活性不是你额外设计的 —— 它是从分解中涌现出来的。单一职责天然赋予你可替换性。

这就是核心信息：技能设计不在于做出"功能最强"的技能 —— 而在于做出"最可分解"的技能。因为纯粹技能组合起来才是真正的力量。

现在来分享一些实用的东西 —— 我每天使用的技能，按类别整理。

首先是 Token 效率。这个简单但强大 —— caveman 压缩输出约 75% 同时保持完整技术准确度。这是我的默认设置 —— 每次对话开始就打开。如果今天只能带走一样东西，明天试试这个。

其次是 编码。这是我花时间最多的地方。我用 Superpowers 技能包，它给了我一整套可组合的开发方法论。每个技能只做一件事 —— brainstorming 澄清需求，writing-plans 做计划，test-driven-development 做 TDD，subagent-driven-development 跑并行 agent，requesting-code-review 做审查，systematic-debugging 做调试。

还有两个额外的：simplify 在写完代码后重构提升清晰度，clonedeps 把依赖源码拉到本地直接查内部实现。

注意这个模式 —— 每个技能处理开发周期的一个阶段。需要什么加载什么，按需组合。

下一类 —— 上下文和基础设施。这是让 agent 有能力从你的内部系统拉取信息。

上下文技能的结构都一样 —— 每个系统一个 CLI 封装。Bitbucket、GitHub、Jira、Confluence、Microsoft Teams —— 每个都是独立技能，精确知道如何和一个系统通信。这就是单一职责在行动。

为什么重要？因为当任务说"审查这个 Jira ticket 对应的 PR"，AI 能自动推断需要 using-jira-cli 获取 ticket 上下文，using-bitbucket-cli 获取代码。你没有硬编码那个组合 —— 它是从每个技能清晰的责任边界中涌现出来的。

这里 声明式原则 起作用了 —— 你的集成技能越声明式，上限越高。描述你需要什么，而不是怎么获取。让 AI 来搞定"怎么"。

基础设施下面，creating-agents-md 是一个单一用途的技能，生成 AGENTS.md 文件 —— 让项目适配 AI。一个技能，一份职责。

接下来 —— 知识库和记忆。这是技能超越"做任务"、开始构建机构记忆的地方。

三层架构。第一层，understand-anything —— 从代码库和文档生成知识图谱。这是我在接手新项目或面对复杂领域时理清思路的方式。输出是交互式图谱，不只是文字。

第二层，using-memvid-cli —— 逐项目知识管理。等我理解了一个项目，我把那层理解存储为压缩记忆，agent 之后可以查询。把它想成"项目专属上下文，按需获取"。

第三层，using-light-rag —— 这超越了单个项目。它管理跨项目、跨领域的知识。当我需要回溯另一个代码库里相似问题是怎么解决的，就看这里。

注意这个分层架构 —— 深度理解输入到项目记忆，项目记忆输入到跨域检索。每一层都是独立技能，边界清晰。可以独立使用，也可以组合。

可组合的 工作流

A 标准 superpowers 流程 brainstorming → writing-plans → subagent-driven-dev → requesting-code-review → simplify

这就是组合真正发光的地方。这些是我每天实际使用的工作流 —— 每个都只是一系列简单、单一职责的技能。

工作流 A 是标准 superpowers 功能开发流程。brainstorm 澄清，plan 分解，并行 agent 执行，review，然后 simplify。

工作流 B 是我的 bug 修复流程。从 Jira 拉上下文，从 memvid 回溯项目知识，用 TDD 先写测试，review，simplify。

工作流 C 最简单 —— 只是两个技能组合。从 GitHub 拉，然后审查。就这样。两个技能，一件事。

工作流 D 是最复杂的 —— 一个从 Confluence 文档开始的功能需求，用 LightRAG 跨域知识增强，然后走完整开发流程。

工作流 E 是研究导向的 —— brainstorm 一个问题，用知识图谱深入理解，然后用 Kami 生成精美文档。

工作流 F 是元的 —— 用技能创建技能。

工作流 G 关于 项目 AI 适配 —— 用 creating-agents-md 生成 AGENTS.md 文件，让任何项目立即适配 AI。一个技能，一份职责：桥接你的代码库和 AI agent。

注意：每个工作流只是同一小套技能的不同组合。技能不变 —— 组合变化。这就是函数式设计的威力。

#函数式 #技能 #感谢

如果今天只能记住一件事，那就是 —— "像写纯函数一样写你的技能。"

这有三层含义。第一，单一职责 —— 一个技能做一件事，覆盖一个领域，把它做好。不写"无所不能"的技能。

第二，可组合 —— 两个简单技能组合在一起，威力不是加法，是乘法。因为 AI 自动推断加载哪些技能，你不需要手动编排。

第三，无副作用 —— 这在函数式思维中同样重要。一个好的技能不应该依赖外部状态或修改全局环境。它应该是自包含的、可预测的、可复用的。

回到最初的那些痛点 —— 技能太多、找不到合适的、不敢自己写。我希望你带走的是：技能并不神秘，它们只是结构化的 prompt。从你最小的痛点开始，写一个做好一件事的技能，然后组合它，迭代它。函数式思维会帮你写好它。

// 补充建议

三个补充建议

🧠 主动管理上下文

别等 AI Agent 来替你管理。

你更清楚哪些信息是关键，哪些可以丢弃。主动压缩、精简、策划。

🦾 AI 是杠杆

不是大脑替代品。

AI 应该 帮你更好地思考 —— 收集信息、对比选项、执行。但思考本身？永远是你的工作。

💰 合适的模型，合适的任务

别每个任务都用最贵的模型。

~80% 的任务 不需要 Opus + thinking。默认用最强的 = 巨大的预算浪费。

三个补充建议。前两个我已经提过 —— 主动管理你的上下文，记住 AI 是你思考的杠杆，而不是替代品。

第三个是 模型选择。我看到一个常见模式：人们总是选最先进的模型 —— 比如 Opus —— 并且每个任务都开启扩展思考。这是巨大的预算浪费。

用 80/20 法则想想。你约 80% 的日常任务不需要最贵的模型。写 commit message、做简单重构、生成样板代码 —— 更快更便宜的模型完全能胜任。把重型武器 —— Opus 级别的模型加扩展思考 —— 留给那 20% 真正需要深度推理的任务：架构决策、复杂调试、精细的代码审查。

这直接关联 token 效率。最贵的 token 是那些你根本不需要消耗的 token。把模型匹配到任务复杂度，是削减 AI 预算最简单的方式之一，而且不牺牲质量。
