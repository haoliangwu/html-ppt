// 第一幕 · 解构

Skill 就是一个结构化的 prompt。
仅此而已。

01
减少重复的 prompt engineering

写一次，到处用。一处维护 —— 所有消费者都受益于更新。

02
实现共享和复用

封装领域知识 → 别人加载 → 开箱即用。不用每个人写自己的版本。

03
从最简单的开始

20 行的 Skill 也是 Skill。先解决你最小的痛点，然后迭代。

但说实话，我觉得 Skills 没有什么神秘的地方。一个 Skill 就是一个结构化的 prompt。如果你会写 prompt，你就会写 Skill。如果你知道怎么做好的 prompt，你就能用好 Skills。

Skill 的最大优势是因为有规范和标准，所以可以被分享和复用。而且我还建议你从最简单的东西开始写自己的 Skill，只要它能解决你的问题就可以。

// 第二幕 · 函数式思维

函数式思维
→ Skill 设计

🧩 单一职责

一个函数只做一件事，并把它做好。

→ 一个 Skill 覆盖一个领域，并把它做好。

"无所不能"的 Skill = 难以维护、复用、组合

🔗 组合

复杂行为从简单函数的组合中涌现。

→ 两个简单 Skill 组合 = 一个更强大的 Skill

AI 自动推断给定任务该加载哪些 Skill

"像写纯函数一样写你的 Skill
   — 单一职责、可组合、无副作用"

我们来聊聊今天分享的核心：函数式思维。

重点在于，无论你在用什么 Skills 还是想创建新的，用函数式思维来指导你的工作都是一个好主意。

函数式思维的两个主要原则是单一职责和组合。

第一个很简单：一个函数只做一件事，并把它做好。所以在 Skill 的世界里，一个 Skill 应该覆盖一个领域，并把它做好。

第二个在函数式编程中更复杂，但核心思想是复杂行为是从简单函数的组合中涌现出来的。所以在 Skill 的世界里，两三个简单 Skills 组合起来就是一个更强大的 Skill。

// 第二幕 · 案例研究

代码审查案例：
两种设计

❌ 非函数式

一个 "巨无霸" 代码审查 Skill：

  • 从 Bitbucket 拉取 PR diff
  • 解析 diff 文件
  • 对照本地代码库分析
  • 生成审查意见
  • ...全在一个文件里

换到 GitHub？重写。换审查策略？重写。

✅ 函数式

拆成 三个 独立 Skill：

  • using-bitbucket-cli — 获取 PR 数据
  • java-best-practices — 审查策略（代码规范、技术栈、性能、安全）
  • requesting-code-review — 描述审查流程（抽象掉"数据从哪来、如何审查"）

换到 GitHub？把 Bitbucket CLI 换成 GitHub CLI。换 Python？换审查策略 Skill。其他 Skill：零修改。

💡 AI 推断是关键 — 它看到"审查这个 Java PR"，就会自动加载 using-bitbucket-cli + java-best-practices + requesting-code-review

左边这种设计把所有东西都耦合在一个 Skill 里，它能用但不高效也不易维护。

右边是更函数式的设计，把 Skill 拆成了三个部分：

1. 数据从哪来、怎么获取

3. 怎么处理审查流程

因为在座的都是工程师或者有技术背景，所以我们可以很容易理解两者之间的区别。右边这种设计更灵活也更容易维护。

节省 Token & 编码

caveman — 压缩约 75% 的输出 token 同时保持完整技术准确度。我每次对话的默认设置。

🛠️ 编码

  • brainstorming — 澄清需求
  • writing-plans — 实现计划
  • test-driven-development — TDD
  • subagent-driven-development — 并行 agent
  • requesting-code-review — 代码审查
  • systematic-debugging — 调试

✨ 重构

simplify — 重构最近编写的代码，提升清晰度和一致性，不改变功能。

clonedeps — 将依赖源码拉到本地，直接检查库内部实现。

首先，Token 效率方面，我用 "caveman" skill 来压缩 AI 的输出。请注意这个 skill 关注的是压缩输出而非输入，因为输入的成本远低于输出的成本。

编码方面，我基本上每天都在用 "superpowers" skill 包，它是一个很强大的 skill 包，覆盖了从需求分析到代码审查的整个开发周期。

我还推荐大家使用 "simplify" skill 在写完代码后进行重构。它的作者和 OpenCode 中的 oh-my-opencode-slim 插件是同一人。我已经用了 OpenCode 一段时间，弃用了 Cursor，因为 OpenCode 开源而且配合 Rakuten 内部 LLM 更省钱。

知识库和记忆管理方面，我用这三种 Skills 分别满足不同的需求：

"understand-anything" 用来从代码库和文档生成知识图谱。

"using-memvid-cli" 用来保存与某个特定项目相关的知识。

"using-light-rag" 是配合 LightRAG 这个轻量级 RAG 框架使用的，用来检索多个项目和业务领域的知识。

有时候我听到有人说 RAG 已经死了，因为模型上下文窗口足够长，可以存储一切。但实际上，我们仍然需要通过语义搜索和向量存储来提供信息的准确性。

// 补充建议

三个补充建议

🧠 主动管理上下文

别等 AI Agent 来替你管理。

你更清楚哪些信息是关键，哪些可以丢弃。主动压缩、精简、策划。

🦾 AI 是杠杆

不是大脑替代品。

AI 应该 帮你更好地思考 —— 收集信息、对比选项、执行。但思考本身？永远是你的工作。

💰 合适的模型，合适的任务

别每个任务都用最贵的模型。

~80% 的任务 不需要 Opus + thinking。默认用最强的 = 巨大的预算浪费。

我还想分享一些关于如何更高效使用 AI Agent 的实际建议。因为时间有限，我不会深入细节，但我觉得背后的动机很容易理解。

第一个是：你应该主动管理 AI Agent 的上下文，而不是把它当成黑盒。至少你要知道你的上下文是如何被使用的：

* 是否有重复或过时的内容？

* 是否有可以丢弃的内容？

* prompt 是否太长、包含了太多不必要的部分？

* Agent 是否因为缺乏上下文或工具而在单个任务上花费太多时间？

如果你不知道它是怎么工作的，你就无法提升 AI Agent 的表现。

第二个是：你应该把 AI 当作杠杆，而不是替代你的大脑。AI 应该帮助你更好地思考、收集信息、对比选项、执行任务。你仍然需要思考和做决策，不要依赖 AI 替你完成一切，发一个 prompt 然后就不管了。

第三个是关于怎么省预算。可能你们也知道，Cursor 的定价已经从按请求次数改成按 token 用量了。我还听到有同事一周甚至两天就跑完了 500 刀的预算。（这对我来说不太合理）

AI 很棒，但不是免费的。你应该明智地使用它并节省预算。

最实用的建议是：用合适的模型处理合适的任务。不要每个任务都用最贵的模型，比如 anthropic opus。大多数情况下，我觉得 sonnet 就够了，甚至 haiku 也行，只要用得对。
